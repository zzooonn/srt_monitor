# 고속철도 통합 모니터 전면 개편 설계

작성일: 2026-10-03 / 상태: 사용자 승인 후 구현·모의 검증 완료

## 1. 목표와 공식 운영 기준

SRT 중심의 화면과 두 철도사별 설정을 하나의 고속철도 여정·계정·감시 흐름으로 개편한다. 작업 범위는 실제 웹 화면, FastAPI 서버, 설정 변환, 관련 테스트, 실행 안내이다.

공식 앱 이름은 **코레일+**이다. 철도산업정보센터는 2026-08-03 앱 출시와 2026-09-01 통합 열차 운행을 안내한다. 국토교통부의 2026-08-31 발표도 기관 통합과 통합 운행을 설명한다.

- 공식 앱 안내: https://www.kric.go.kr/jsp/video/railMedia/railMediaDetail.jsp?p_id1=68
- 국토교통부 발표 원문 요약: https://eiec.kdi.re.kr/policy/materialView.do?num=286017&pg=1&pp=20&topic=P

운영 통합 사실만으로 기존 SRT·korail2 라이브러리의 인증 방식, 서버 주소, 응답 규격이 동일하다고 단정하지 않는다. 계정과 조회는 코레일 연결을 기본으로 하되, 실제 연결 성공과 통합 구간 조회 범위는 별도로 검증한다.

## 2. 현재 코드에서 확인한 문제

- 실제 화면은 `backend/app.py`가 제공하는 `SRT Monitor _standalone_.html`이다. 현재 디렉터리에 `frontend/`는 없으며, 기존 README의 Vite 안내는 실제 실행 구조와 다르다.
- 화면 소스 `extracted_app.js`에는 SRT 브랜딩, SRT 계정 필수 검사, KTX 토글, 별도 서비스 상태 카드가 남아 있다.
- 서버에는 SRT·KTX 각각의 구간과 좌석종류 설정이 있다. KTX 감시는 기본적으로 꺼져 있고, SRT 시작은 항상 시도한다.
- KTX 역 목록에는 수서·동탄·평택지제가 없어 통합 구간 검색을 시작하기 전에 차단한다. 경주·신경주도 중복 표기된다.
- 통합 상태의 `phase`는 SRT 상태만 사용해 KTX만 동작할 때 잘못된 상태를 전달할 수 있다.
- 기존 예약 조정자는 중복 시도와 불확실한 예약 결과를 보호한다. 이 보호는 개편 후에도 유지해야 한다.
- 실행 환경의 Python에는 pytest가 설치되어 있지 않아 기존 테스트의 통과 여부는 아직 확인하지 못했다.

## 3. 접근 방식 비교와 선택

| 방식 | 결과 | 한계 |
| --- | --- | --- |
| 문구와 색상만 교체 | 화면 명칭 빠르게 정리 | SRT 필수 계정, 분리 설정, 통합 구간 차단이 남음 |
| **통합 여정 모델 + 코레일 기본 연결** | 화면·설정·감시를 함께 일치시키고 기존 예약 로직 재사용 | 설정 변환과 통합 상태 정리가 필요함 |
| 모든 조회·예약 엔진을 새로 작성 | 내부 구조까지 완전히 교체 | 검증된 좌석·타임아웃 처리 회귀 위험과 외부 API 불확실성이 큼 |

두 번째 방식을 권장한다. 실제 사용자 흐름을 전면 개편하고, 검증 가능한 기존 예약·좌석 로직은 연결 모듈 내부에서 재사용한다.

## 4. 화면 설계

제품명은 **Rail Monitor / 고속철도 통합 모니터**로 사용하고, 설명에 ‘코레일+ 통합 운행 기준’을 표시한다. 공식 앱 명칭은 서비스 설명과 예약 확인 안내에 사용한다.

밝은 배경, 짙은 남색, 청록색 강조, 명확한 글자 크기로 구성한다. 큰 여정 입력 영역과 오른쪽 실행 요약을 중심으로 데스크톱 화면을 만들고, 모바일에서는 세로로 쌓는다.

사용 순서:

1. 출발·도착역, 날짜, 출발 시간 범위를 한 번 입력한다.
2. 승객 유형별 인원, 일반실·특실, 연석·창가 조건을 설정한다.
3. 코레일 통합 계정과 선택적인 텔레그램 알림을 설정한다.
4. ‘알림만 받기’ 또는 ‘자동 예약’을 선택하고 감시를 시작한다.
5. 통합 상태, 예약 수, 최근 조회 시각, 실제 이벤트를 확인한다.

메인 화면에서 SRT·KTX별 토글과 별도 계정 필수 검사를 없앤다. 구형 SRT 연결은 ‘고급 설정 > 이전 SRT 연결’에서 명시적으로 선택하도록 둔다. 통합 계정 비밀번호를 SRT 연결에 복사하거나 두 연결을 자동으로 동시에 실행하지 않는다.

예약 결과가 불확실하면 ‘코레일+에서 예약 내역 확인’ 안내와 ‘예약 있음 / 예약 없음’ 버튼을 제공한다. 구형 연결이 만든 불확실 상태에는 기존 SRT 예약 내역 확인 안내를 사용한다.

역 목록은 서버에서 받아 화면과 서버가 같은 데이터를 사용한다. 임의의 예약 성공, 좌석 발견, 연결 정상 상태를 표시하지 않는다. 날짜·시간·인원·좌석 검증 오류는 해당 입력 주변에 표시한다.

## 5. 서버 구성

### 통합 설정

공개 설정은 하나의 `departure_station`, `arrival_station`, 날짜·시간, 승객, 좌석 조건, 예약 정책을 사용한다. `connection_mode`는 `korail`을 기본으로 하고 명시적으로 `legacy_srt`를 선택할 수 있다. 새 설정은 `schema_version=2`로 구분한다.

코레일 연결은 `korail_id`와 `korail_password`를 사용한다. 공개 API에는 계정 값이 포함되지 않고, 설정 여부만 응답하는 기존 분리를 유지한다. SRT 자격증명은 구형 연결용으로 보존한다.

공개 설정 단계에서 실제 달력 날짜, 00~23시·00~59분, 시작·종료 순서, 다른 출발·도착역, 총 승객 1~4명, 하나 이상의 좌석종류를 검증한다. 화면에서 수정하지 않은 승객 유형·알림 주기 설정을 저장할 때 지우지 않는다.

### 통합 감시 서비스

새 통합 서비스가 시작·중지·상태·이벤트의 단일 진입점이 된다. 코레일 또는 구형 SRT 연결을 선택해 기존 엔진에 공통 여정 설정을 전달한다. 기본 코레일 모드에서는 기존 KTX 옵션이 꺼져 있어도 코레일 감시를 시작한다.

코레일 연결 내부는 기존 `ktx_monitor_service.py`와 `ktx_logic.py`의 조회·예약·승객 처리 기능을 재사용한다. 구간은 공통 여정 설정으로 전달하고 통합 고속철도 역 목록을 적용한다. 열차 종류가 실제 응답에서 고속철도인지 확인하여 일반열차가 섞이지 않게 한다. 실패 응답은 연결 오류로 표시하고 구형 연결로 자동 재시도하지 않는다.

예약은 기존 `ReservationCoordinator`를 통과한다. 목표 수 도달 시 추가 예약을 차단하고, 타임아웃·취소 여부 불확실 상황은 확인 필요 상태로 남긴다. 중지·재시작으로 확인 필요 상태를 지우지 않는다. 기존 조정자의 프로세스 재시작 이후 영속성 한계는 실행 안내에 명시한다.

### 상태와 API

`/api/start`, `/api/stop`, `/api/status`, `/api/events`, `/api/events/stream`, 공개·비밀 설정 API, 예약 결과 확인 API는 현재 경로를 유지한다. 새 화면은 통합 상태와 연결 정보를 사용한다.

전체 상태는 실제 실행 연결과 예약 잠금에서 계산한다. 확인 필요, 예약 중, 목표 달성, 오류, 조회 중, 중지, 대기를 구별한다. 이전 `srt`·`ktx` 상태 필드는 호환 기간에 남기되, 전체 상태를 SRT 상태에서 그대로 복사하지 않는다.

새 `/api/stations`는 통합 검색 목록과 정규 역명을 제공한다. 경주·신경주 등 별칭은 입력 정규화로 흡수한다. 역 이름은 검증된 목록에서 제공하며 두 역이 존재한다는 이유만으로 직통 열차가 있다고 표시하지 않는다. 실제 운행 없음은 조회 결과로 표현한다.

## 6. 기존 설정 변환

최초 변환 전에 원본 설정을 백업한다. 비밀번호와 토큰은 출력·문서에 포함하지 않는다. 설정 저장은 임시 파일을 작성한 뒤 교체해 중간 실패로 원본이 손상되지 않게 한다.

- 기존 공통 여정, 날짜·시간, 승객 유형, 좌석 조건, 예약 정책, 알림 설정을 보존한다.
- 기존 KTX 감시가 활성화되어 있고 별도 KTX 구간이 있으면 그 구간을 통합 여정으로 우선 이전한다. 두 구간이 달랐으면 화면에 이전에 선택한 여정을 설명한다.
- 코레일 계정이 있으면 기본 코레일 연결을 사용한다.
- SRT 계정만 있으면 계정을 보존하고 코레일 통합 계정 설정이 필요함을 안내한다. 계정 통합을 앱이 대신 수행하거나 SRT 자격증명을 코레일 계정으로 간주하지 않는다.
- 구형 SRT 연결은 사용자가 고급 설정에서 선택할 때 실행한다.
- 오래된 필드가 포함된 설정 저장 요청에도 같은 변환 규칙을 적용해 기존 클라이언트가 새 필드를 기본값으로 덮어쓰지 않게 한다.

## 7. 프론트 소스와 실행 안내

압축된 24MB HTML을 직접 수정하는 흐름을 정리하고 `frontend/`에 읽고 편집할 수 있는 HTML·CSS·JavaScript 소스를 둔다. FastAPI에서 정적 파일을 제공해 기존 `http://127.0.0.1:8000/` 주소로 실행한다. 새 화면을 위해 Node 설치나 별도 프론트 개발 서버를 요구하지 않는다.

기존 단독 HTML과 추출 소스는 전환 중 원본으로 보존한다. 새 화면은 설정 로드·저장, 감시 시작·중지, 이벤트 재연결, 예약 확인 기능을 모두 현재 API와 연결한다.

`README.md`, `WEB_README.md`, 웹 실행·설치 배치 파일의 제품명과 설명을 실제 구조에 맞춰 갱신한다. CLI 및 기존 실행파일의 예약 엔진 재작성은 웹 개편 범위에 포함하지 않는다.

## 8. 구현 및 검증 순서

1. 테스트 실행 환경을 확보하고 기존 테스트를 실행한다. 기존 설정을 건드리지 않는 임시 설정 파일로 검증한다.
2. 설정 변환·통합 역 목록·통합 서비스·상태 계산을 구현하고 관련 회귀 테스트를 추가한다.
3. 새 프론트 화면을 작성하고 실제 API와 연결한다.
4. 설정 보존, 코레일 단독 시작, 수서·동탄 구간 전달, 구형 SRT 명시 선택, 불확실 예약 차단, 중지·재시작, SSE 이벤트를 모의 연결로 검증한다.
5. 데스크톱·모바일 화면에서 설정 저장·복원과 상태·오류 표시를 확인하고 실행 문서를 갱신한다.

실계정 로그인·실제 통합 구간 조회·실제 예약은 각각 별도 검증 항목이다. 모의 테스트의 통과를 실계정 예약 성공으로 보고하지 않는다. 검증 과정에서 실제 예약·취소를 실행하지 않는다.

## 9. 완료 기준

메인 화면에 SRT 전용 서비스로 보이는 문구나 필수 계정 조건이 없고, 하나의 여정과 코레일 계정으로 감시를 시작할 수 있어야 한다. 통합 고속철도 역을 서버와 화면에서 동일하게 제공하고, 기존 사용자 설정을 보존하며, 실제 엔진 상태와 예약 불확실성을 정확하게 표시해야 한다. 관련 테스트 및 브라우저 점검 결과와 외부 연결의 미검증 범위를 함께 보고한다.
